369: 3.1 Реализация серверной части CRM-системы
370: После завершения этапа проектирования была реализована серверная часть CRM-системы, обеспечивающая работу ВКонтакте-бота, административной панели и базы данных. Серверная часть является центральным компонентом системы, поскольку именно в ней сосредоточена основная бизнес-логика: обработка записей, управление статусами, расчет свободных слотов, ведение клиентской базы и формирование уведомлений.
371: В качестве технологической основы backend-части был использован язык программирования Python и фреймворк FastAPI. Выбор FastAPI обусловлен его удобством при разработке REST API, поддержкой типизации, высокой скоростью обработки запросов и возможностью быстро создавать структурированный backend для MVP-проекта. Для хранения данных была выбрана СУБД PostgreSQL, позволяющая надежно хранить структурированную информацию о клиентах, мастерах, услугах и записях.
372: Серверная часть реализует набор API-маршрутов, предназначенных для работы с основными сущностями системы. В частности, реализованы маршруты для:
373: работы с клиентами;
374: работы с категориями услуг;
375: работы с услугами;
376: работы с мастерами;
377: работы с расписанием;
378: работы с записями;
379: работы с уведомлениями;
380: получения сводной статистики;
381: приема событий от ВКонтакте-бота.
382: Одной из ключевых функций backend является управление записями. При создании записи сервер принимает данные о клиенте, услуге, мастере, дате и времени, после чего выполняет несколько проверок:
383: существует ли выбранная услуга;
384: может ли выбранный мастер выполнять указанную услугу;
385: является ли выбранное время рабочим временем мастера;
386: не пересекается ли новая запись с уже существующими;
387: не относится ли выбранный слот к уже прошедшему времени.
388: Только после успешного прохождения всех проверок система создает запись в базе данных и присваивает ей соответствующий статус. Это дает возможность избежать конфликтов в расписании и повышает надежность работы CRM-системы.
390: Рисунок 5 - Фрагмент кода модели записи клиента
392: Отдельное внимание в реализации серверной части было уделено логике переноса и отмены записей. Для переноса записи сервер повторно рассчитывает доступность нового временного слота с учетом уже существующих записей и статуса текущего визита. Для отмены записи предусмотрены ограничения: отменять можно только запись в допустимом состоянии, а отмененные записи не должны повторно участвовать в логике активных визитов и уведомлений.
394: Рисунок 6 - Фрагмент кода логики создания записи
395: Также в backend была реализована система уведомлений. Она предназначена для:
396: отправки подтверждения после создания записи;
397: уведомления клиента о переносе записи;
398: уведомления клиента об отмене записи;
399: напоминания о визите за 24 часа;
400: напоминания о визите за 2 часа.
401: Для уведомлений используется отдельная сущность, содержащая тип уведомления, время отправки, текст сообщения и статус обработки. Это дает возможность централизованно управлять служебными сообщениями и контролировать жизненный цикл уведомлений.
402: Дополнительно в серверной части был реализован механизм административной аутентификации. Доступ к защищенным маршрутам API получают только авторизованные пользователи административной панели. Это необходимо для защиты клиентских данных и ограниченного доступа к операциям по управлению записями и каталогом услуг.
403: В результате серверная часть CRM-системы реализует все основные функции, необходимые для работы MVP-проекта, и обеспечивает взаимодействие между ботом, административной панелью и базой данных.
404: 3.2 Реализация ВКонтакте-бота для автоматизации записи клиентов
405: Клиентский интерфейс разрабатываемой системы реализован в форме ВКонтакте-бота, встроенного в сообщество салона красоты. Бот служит основной точкой взаимодействия клиента с системой и обеспечивает выполнение типовых пользовательских сценариев без необходимости перехода на внешний сайт или установки дополнительного приложения.
